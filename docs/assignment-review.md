# B4-2 요구사항 정밀 검토

## 판정

필수 3개 사례의 제출 증거와 보고서 구조를 충족한다. 각 비교에서 과제 환경변수를 하나씩 바꾸었고, 원본 로그·관측 파일·종료 기록을 연결했다. 선택 과제인 스케줄링 알고리즘 추론은 정상 시나리오 로그 2건으로 수행했다. 이 판정은 과제 문구와 제출물을 대조한 자체 검토이며 평가자의 점수나 학습자의 설명 능력을 보증하지 않는다.

## 검토 후 보완한 사항

1. 보고서마다 재현 명령을 추가하고 메모리 구조와 시스템 영향 설명을 보강했다.
2. 검증 도구가 이전 원본 해시를 먼저 확인하도록 변경했다. 일반 실행은 읽기 전용이며, `--refresh`도 기존 원본 변조가 있으면 거부한다.
3. 요약 JSON을 그대로 믿지 않고 원본 TSV·top·종료 기록과 대조하며, 비교 쌍의 환경변수·바이너리 해시도 검사한다.
4. Git의 Windows 줄바꿈 변환으로 증거 바이트가 달라지지 않도록 evidence 전체를 변환 대상에서 제외했다. 실행 스크립트는 LF로 관리한다.

## 남겨 둔 한계

- 생존 시간은 실험 스크립트가 기록한 전체 시간이다. 부팅·관측 확인·종료 처리 시간이 포함되며 정밀한 장애 발생 지연 측정값은 아니다.
- CPU_MAX_OCCUPY 변경 시 실행되는 워커 구성이 달라진다. 확인한 효과는 해당 설정에서의 보호 종료 회피이며 동일한 작업량에 대한 성능 향상 주장은 하지 않는다.
- 멀티스레드 옵션을 false로 해도 정상 경로에 작업 스레드가 존재한다. 옵션 이름만으로 실제 스레드 수를 추정하지 않는다.
- 각 설정의 관찰은 짧은 실습이다. 무기한 정상 동작, 생산 환경 안정성, 사용자 요청 지연 개선은 검증하지 않았다.
- GitHub Issue 구조의 Markdown을 레포에 제출한다. 같은 내용을 레포의 GitHub Issues #1~#4에도 등록했다.
- 스케줄링 추론은 애플리케이션 `[Scheduler]`의 작업 처리 순서에 대한 것이며 Linux 커널 스케줄러 정책을 단정하지 않는다. 등록 순서와 우선순위가 같을 가능성은 로그만으로 배제하지 못한다.

## 설명 연습

제출 전 아래 질문을 자신의 말로 설명할 수 있으면 과제의 학습 목표와 연결된다.

- 왜 실행용 부모 PID만 보면 메모리 증가를 놓치는가? 실제 데이터를 할당하는 자식의 RSS를 관측해야 하기 때문이다.
- 메모리 한도를 두 배로 올렸는데 왜 해결이 아닌가? 할당 누적은 계속되고 종료 시점만 늦춰졌기 때문이다.
- Current Load 50%와 top 5%가 왜 다른가? 애플리케이션 내부 표시와 OS의 구간 집계는 다른 지표이며, 측정 간격도 영향을 주기 때문이다.
- 종료 코드 143만 보고 Watchdog라고 할 수 있는가? 누가 종료했는지 알 수 없으므로 정책 로그와 스크립트의 중단 기록이 필요하다.
- CPU 0%인 프로세스가 모두 교착상태인가? 정상 대기도 가능하므로 PID 유지, 로그 정체, 자원 보유와 순환 대기를 함께 확인해야 한다.
