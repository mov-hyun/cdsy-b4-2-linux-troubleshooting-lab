# 장애 치명도·우선순위 기준과 동시 장애 대응 절차

세 리포트에 같은 기준으로 치명도와 우선순위를 매기고, 여러 장애가 동시에 보고될 때 무엇부터 처리할지 정한다.

## 1. 치명도(Severity) 기준

네 가지 축으로 판단한다. **서비스 영향**, **탐지 가능성**(프로세스 감시만으로 알 수 있는가), **확산 가능성**(다른 프로세스·호스트 자원까지 번지는가), **복구 방법**(자동 재시작으로 되는가, 검증된 임시 조치가 있는가).

| 등급 | 정의 |
| --- | --- |
| SEV1 Critical | 서비스가 완전히 멈췄는데 프로세스는 정상처럼 보여 자동 탐지·자동 재시작이 되지 않는다. 또는 데이터 손실·보안 사고. |
| SEV2 Major | 서비스가 중단되지만 종료가 명확히 관측되고 재시작으로 일시 복구된다. 원인이 남아 있어 재발이 확실하다. |
| SEV3 Minor | 성능 저하나 일부 기능 영향. 서비스는 유지된다. |
| SEV4 Low | 사용자 영향 없음. 관찰·개선 대상. |

## 2. 우선순위(Priority) 산정

1. 치명도에서 시작한다. SEV1은 P1, SEV2는 P2, SEV3는 P3, SEV4는 P4다.
2. 호스트 공유 자원(메모리, 디스크)을 고갈시켜 다른 서비스로 번질 수 있으면 한 단계 올린다.
3. 검증된 임시 조치가 이미 적용됐으면 한 단계 내린다. 근본 해결 일정은 그대로 둔다.
4. 같은 등급 안에서는 재발 주기가 짧은 장애를 먼저 처리한다.

## 3. 이번 장애 3건 적용

| 리포트 | 서비스 영향 | 탐지 가능성 | 확산 가능성 | 복구 | 치명도 | 우선순위 |
| --- | --- | --- | --- | --- | --- | --- |
| [교착상태](../reports/03-deadlock.md) | 완전 무응답. PID와 포트 15034 유지 | 어려움. PID·CPU·메모리가 정상처럼 보이고, 로그 정지로만 탐지(STALL 15초) | 낮음. CPU·메모리를 더 쓰지 않음. 대신 요청이 쌓임 | 자동 복구 없음. 수동 종료 후 `MULTI_THREAD_ENABLE=false` | SEV1 | P1 |
| [메모리 누수](../reports/01-memory-oom.md) | 수 초마다 강제 종료(137) | 쉬움. 종료 로그, RSS 경보가 2초 먼저 | 높음. 한도를 올릴수록 호스트 메모리를 더 차지 | 재시작·한도 상향은 종료를 늦출 뿐 | SEV2 | P2 (확산 +1, 임시 조치 −1) |
| [CPU 과점유](../reports/02-cpu-watchdog.md) | 약 28초 후 Watchdog 종료(143) | 종료는 쉬움. OS CPU 지표로 사전 탐지는 불가 | 낮음. 같은 시각 호스트 idle 96% 이상 | `CPU_MAX_OCCUPY=40`으로 관찰 기간 동안 회피 검증 | SEV2 | P3 (임시 조치 −1) |

교착상태를 가장 높게 둔 이유는 "조용한 장애"이기 때문이다. 종료형 장애는 감시 도구가 재시작이라도 하지만, 교착은 누군가 로그 정지를 알아채기 전까지 계속된다.

## 4. 동시 장애 대응 절차

이 앱은 실행 한 번에 시나리오 하나만 나타나므로, "동시 장애"는 여러 인스턴스나 호스트에서 서로 다른 장애가 한꺼번에 보고되는 상황을 뜻한다.

| 단계 | 할 일 | 기준 |
| --- | --- | --- |
| 1. 선언 | 첫 알림 수신자가 장애를 선언하고 지휘자(Incident Commander) 1명을 정한다. 지휘자는 직접 고치지 않고 우선순위·인력·통지를 맡는다. | 알림 후 5분 이내 |
| 2. 증거 보존 | 재시작하기 전에 인스턴스마다 `ps -ef`, `ps -L -o pid,tid,stat,wchan:32`, `top -b -H -n 1`, 로그 마지막 100줄, `thread-waits` 스냅샷을 남긴다. | 인스턴스당 1분 이내. 재시작부터 하면 원인이 사라진다. |
| 3. 분류 | 장애마다 1절 기준으로 치명도를 매긴다. | 증거 확보 직후 |
| 4. 순서 결정 | 아래 규칙을 위에서부터 적용하고, 같으면 다음 규칙으로 넘어간다. ① 데이터 손실·보안 위험 ② 우선순위 등급 ③ 다른 장애의 원인이 될 수 있는가(예: 메모리 고갈 → 스왑 → CPU 지연) ④ 영향받는 요청·사용자 수 ⑤ 검증된 임시 조치가 있어 빨리 끝나는가 | 지휘자가 결정하고 공지 |
| 5. 담당 지정 | 장애 하나에 담당자(Owner) 1명. 한 사람이 두 장애를 동시에 맡지 않는다. 인원이 부족하면 낮은 순위 장애는 임시 조치만 적용하고 대기시킨다. | 순서 결정과 함께 |
| 6. 통지 | 채널 하나로 모은다. 첫 공지는 선언 후 10분 이내. 이후 SEV1은 15분, SEV2는 30분, SEV3는 60분마다 현재 상태·다음 행동·예상 시각을 알린다. | 해결 시 종료 공지 |
| 7. 완화 | 순위대로 임시 조치를 적용한다. | 아래 예시 |
| 8. 검증·종료 | 장애마다 Before/After 지표를 확인한 뒤 종료를 선언한다. | 경보 해소(`RESOLVED`)와 로그 진행 확인 |
| 9. 사후 조치 | 장애별 Issue를 이 레포 리포트 형식으로 작성하고, 근본 개선에 담당자·기한을 붙여 등록한다. 회고를 남긴다. | 종료 후 영업일 기준 2일 이내 |

### 세 장애가 동시에 보고된 경우의 완화 순서

1. **P1 교착:** 증거를 보존하고 `kill -TERM`을 보낸다. 끝나지 않으면 `kill -KILL`. `MULTI_THREAD_ENABLE=false`로 재기동한 뒤 작업 로그가 다시 이어지는지 확인한다.
2. **P2 메모리 누수:** `MEMORY_LIMIT`을 올려 시간을 번다. `ALERT_RSS_KIB`를 새 한도의 80%로 맞춰 재발을 미리 알게 한다. 호스트 전체 여유 메모리를 함께 본다(확산 위험).
3. **P3 CPU 과점유:** `CPU_MAX_OCCUPY=40`을 적용하고 Watchdog 종료 로그가 더 나오지 않는지 확인한다.

규칙 ③에 따라 메모리 누수가 호스트 스왑을 일으켜 다른 인스턴스의 CPU 지연까지 부르고 있다면, 메모리 누수를 교착보다 먼저 완화할 수 있다. 판단 근거는 공지에 남긴다.
